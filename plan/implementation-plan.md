# HowBlog 2.0 实施推进方案

## 1. 文档目标

本方案用于把项目从“能够编译、可以进行基础接口对接”的开发状态，推进到“身份可信、行为可验证、配置可复现、可以持续迭代”的博客后端。

- 建立日期：2026-09-22
- 当前接口契约 revision：5
- 当前契约版本：3.0.0
- 适用范围：`how_common`、`how_user`、`how_base`、`how_article` 及配套文档
- 配套进度：见 [progress.md](progress.md)

## 2. 当前基线

### 已完成

- Maven 多模块结构可用，业务模块职责已基本分离。
- 持久化已统一到 Spring Data JPA，当前使用 Spring Boot 2.7.18、`javax.persistence` 和 Java 21。
- 已移除 MongoDB、MyBatis-Plus 和外部环信依赖。
- `how_user` 已具备轻量 Spring WebSocket IM。
- 评论按文章查询路径已固定为 `GET /comment/article/{articleId}`，解决了与按评论 ID 查询的映射冲突。
- REST、WebSocket、数据模型和已知限制已形成前端接口契约，当前 revision 为 5；文档包已推送至后端 GitHub 仓库，用户确认前端可直接读取 `docs/`。
- AUTH-01 至 AUTH-07 已完成本轮范围：JWT、密码脱敏、作者归属、用户级点赞、WebSocket 鉴权、统一异常及基础输入校验。
- JDK 21 下全模块 `mvn clean test` 通过，共 74 项测试，其中 55 项为真实 MVC/Service 配合模拟 DAO/Redis 的切片测试；尚未完成真实存储联调。

### 当前主要问题

1. JWT 尚无刷新、退出和服务端主动撤销机制，上线要求待确认。
2. 未登录用户仍可能保留明文密码；当前只在成功登录时升级，未批量迁移。
3. 标签写接口仅要求认证，管理员角色尚未建立。
4. WebSocket 已校验 JWT，但 URL token、内存消息和单实例仍有生产限制。
5. 基础输入与资源边界已覆盖；文本长度、状态枚举、关联资源存在性等约束尚未全面实现。
6. 控制器错误响应已脱敏；生产日志策略、关联 ID 和可观测性仍待完善。
7. 数据库、Redis 和其他运行配置需要进一步环境变量化；部署还不可复现。
8. 评论点赞跨 Redis 和 MySQL，仍需明确并发、失败补偿和一致性策略，并验证真实存储行为。

## 3. 推进原则

- **先收口身份，再扩展业务**：所有需要用户归属的行为先建立可信用户上下文。
- **每个行为变更都配验证**：新增或修改业务行为必须同步增加单元测试或集成测试。
- **接口契约与代码同批更新**：REST、WebSocket、错误码、认证方式变化时，同步更新 `docs/frontend-api.md`、`docs/frontend-api-changelog.md` 和 `docs/frontend-api-status.json`。
- **保持模块边界**：公共模块只放跨业务的抽象和工具，不引入具体业务模块依赖。
- **不执行破坏性数据操作**：数据库结构变更先评估兼容性，初始化脚本保持可重复执行，不在开发推进中直接删除或批量修改现有数据。
- **小步交付**：每个实施切片都要有明确输入、输出、验收命令和回滚边界。

## 4. 分阶段路线

### Phase 0：基线整理（当前已基本完成）

目标：确认工程结构、构建入口和接口事实来源。

工作项：

- 保持 JDK 21 和 Spring Boot 2.7.18 版本约束。
- 维护多模块编译和启动说明。
- 维护前后端接口契约及 revision。
- 记录外部依赖：MySQL、Redis，以及 IM 的开发态限制。

完成标准：

- `mvn clean compile` 成功。
- `mvn test` 可执行，并明确记录当前测试数量和覆盖空白。
- 前端可以从接口文档包读取当前 revision 和变更记录。

### Phase 1：身份认证与安全边界（P0，进行中）

目标：建立可靠的登录态，并让所有用户相关操作使用服务端识别的当前用户。

实施顺序：

1. 设计认证契约：登录请求/响应、令牌有效期、刷新和退出策略、认证失败错误码。
2. 增加登录请求 DTO 和安全响应 DTO，禁止直接把 JPA 实体作为登录响应。
3. 使用 BCrypt 等成熟密码哈希方案；规划已有明文密码的迁移策略，不在未确认数据备份前执行批量改密。
4. 增加 JWT 或等价的无状态令牌校验，并把当前用户信息放入统一请求上下文。
5. 保护文章、评论、标签等写接口，明确作者、评论者和管理员权限边界。
6. 评论点赞从固定用户 ID 改为当前认证用户 ID；重复点赞、评论不存在、计数更新失败都返回稳定业务结果。
7. WebSocket 握手校验令牌，移除对 URL `user` 参数作为可信身份的依赖；保留兼容过渡期时必须明确截止条件。
8. 登录成功响应脱敏，至少不返回 `password`。

验收标准：

- 未认证请求不能调用受保护的写接口。
- 登录成功得到令牌，登录失败不会泄露用户是否存在的敏感细节。
- 任意两个用户可以分别对同一评论点赞；同一用户重复点赞被拒绝。
- 客户端不能通过修改 URL 用户名冒充其他用户建立 IM 身份。
- 认证相关异常不会返回堆栈、SQL 或内部连接信息。
- 接口文档 revision 已递增，前端可以按 changelog 完成迁移。

首个实施切片及 AUTH-07 已完成，当前进入角色权限与会话策略收口。不要在这一阶段同时加入注册、关注等新业务。

### Phase 2：测试与数据一致性（P1）

目标：让关键行为可重复验证，并处理跨存储操作的失败和并发问题。

工作项：

- 为登录、文章分页搜索、标签 CRUD、评论路径、评论新增和点赞增加 JUnit 5 测试。
- 优先使用 Testcontainers 覆盖 MySQL 和 Redis；无法使用容器时提供明确的本地集成测试配置。
- 测试资源不存在、重复操作、空输入、越界分页和未认证访问。
- 评论点赞保持数据库端原子计数更新，并定义 Redis 标记与数据库更新失败时的补偿或重试策略。
- 把字段注入逐步替换为构造器注入，优先覆盖认证和点赞链路。
- 统一异常映射，避免将 `Exception#getMessage()` 直接作为公共错误消息。

验收标准：

- `mvn test` 至少执行一组真实行为测试，而不是只有编译成功。
- 关键测试在干净环境重复运行结果一致。
- 点赞并发和 Redis/数据库单点故障的预期结果已经由测试或运行手册说明。

### Phase 3：配置、部署与可观测性（P1）

目标：让新环境能够安全、可复现地启动和诊断。

工作项：

- 将 MySQL、Redis、JWT 密钥、CORS 来源和服务端口改为环境变量或本地未跟踪覆盖配置。
- 提供脱敏的示例配置和本地启动说明。
- 增加 Docker Compose，至少覆盖 MySQL、Redis 和三个业务服务的开发启动路径。
- 增加健康检查、结构化日志和请求关联 ID；禁止日志打印密码、令牌和完整敏感请求体。
- 在 CI 中执行 JDK 21 下的编译、测试、接口文档检查和敏感信息扫描。

验收标准：

- 新环境不需要修改提交到仓库的真实凭证即可启动。
- 服务依赖不可用时能快速判断是配置、连接还是业务错误。
- CI 能阻止编译失败、测试失败和明显的凭证误提交。

### Phase 4：博客核心产品能力（P2）

目标：在安全和测试底座稳定后补齐用户可见的博客工作流。

建议顺序：

1. 用户注册、资料维护、头像和账号基础能力。
2. 文章草稿、发布、审核状态和作者权限。
3. 标签关联、文章筛选和可扩展搜索。
4. 文章浏览量、文章点赞、收藏和关注。
5. 评论树、评论删除权限、审核和通知。

每项能力都应先定义数据模型、权限规则、接口契约和验收测试，再实现 Controller。

### Phase 5：IM 生产化（P2）

目标：把当前进程内开发态 IM 演进为可部署的协作能力。

工作项：

- Redis 或消息中间件广播，支持多实例。
- 消息持久化、离线消息和已读状态。
- 连接鉴权、消息大小限制、频率限制和输入清理。
- 断线重连、重复消息处理和连接生命周期监控。
- 明确音视频、文件传输、好友/群组是否属于后续范围。

## 6. 接口契约发布规则

只要改变以下任一项，就必须同步更新接口文档包：

- 路由、HTTP 方法、路径参数或查询参数。
- 请求体、响应体、字段类型、错误码或错误行为。
- 认证方式、CORS、端口或网关前缀。
- WebSocket 连接参数、客户端消息或服务端事件。

发布步骤：

1. 修改代码前读取当前 `docs/frontend-api-status.json`，确认 revision。
2. 同批更新 `docs/frontend-api.md`。
3. 在 `docs/frontend-api-changelog.md` 末尾追加记录，不改写历史条目。
4. 递增 revision，并更新状态文件中的影响范围和前端动作。
5. 运行适用的编译/测试，核对文档没有记录未实现行为。
6. 在交付说明中写明新的 API revision 和文档发布位置。

## 7. 完成定义

一个阶段只有同时满足以下条件才可以标记为完成：

- 代码、配置、数据库影响和接口契约已同步。
- 关键成功、失败和边界路径有自动化验证，或已记录明确的外部依赖限制。
- `mvn` 编译和适用测试通过。
- 没有新增明文凭证、令牌、密码或未审查的远程连接信息。
- 进度文件记录了完成项、验证结果、剩余风险和下一步。

## 8. Phase 1 初始认证决策

以下决策于 2026-09-22 建立，用于启动 AUTH-02；未解决事项保留在下一节，不阻塞登录边界修复。

- 登录标识使用 `mobile`。认证查询若得到零条或多条记录，均按登录失败处理，避免重复手机号对应到不确定账户；后续需要通过数据库迁移补充唯一性约束。
- 现有实现按原始密码精确查询，暂按“存量密码为明文”处理。不得执行批量改密；仅在用户使用正确的旧密码成功登录时，将该密码升级为 BCrypt 哈希。
- 登录请求只接受 `mobile` 和 `password`；为了让旧客户端平滑过渡，额外 JSON 字段在反序列化时忽略，不再参与认证查询。
- 登录响应使用显式的安全 DTO，保留必要的非敏感用户资料，永不返回 `password`。
- 令牌采用由 `how_user` 签发的 Bearer JWT；密钥只允许从环境变量读取，令牌签发、校验和刷新策略在 AUTH-03 实现。
- 角色模型当前尚未存在于用户表。AUTH-03 先建立“已认证用户”上下文；文章、评论和标签的作者/管理员授权规则在接入写接口前单独确定。

### 8.1 已落地的 Phase 1 决策

- 当前使用 HS256 Bearer JWT，默认访问令牌有效期为 1800 秒；三个业务服务通过 `HOW_AUTH_JWT_SECRET` 共享至少 32 字节的密钥。
- `POST /user/login` 签发访问令牌；当前不提供刷新 token、退出登录或服务端主动撤销接口。
- 文章、评论、标签写接口要求已认证；文章和评论的修改/删除校验作者归属，标签暂时没有管理员角色区分。
- WebSocket 使用 `/im?token=<url-encoded-token>` 握手，旧的 `?user=` 不再作为可信身份来源。
- 评论点赞先以 `userId + commentId` 在 Redis 中原子占位，再执行 MySQL 原子计数；失败时会尝试释放占位，但跨存储提交一致性仍需 Phase 2 完善。
- 认证改造对应 API revision `4`（contract version `2.0.0`）；当前 AUTH-07 已同步 revision `5`（`3.0.0`），因输入与错误边界变化标记为破坏性变更，外部发布渠道待确认。
- AUTH-07 使用新增/编辑校验分组保留部分更新；统一 400/404/500 错误响应，分页限制为 `page >= 1`、`1 <= size <= 100`；现有作者权限响应保持不变。

## 9. 当前决策待确认项

这些问题会影响后续 Phase 1 实现，开始对应任务前应在进度文件中记录决定：

- JWT 访问令牌默认 1800 秒已确定；刷新令牌持久化、退出和撤销策略及其上线优先级待确定。
- 现有数据库中是否存在不符合当前明文假设的历史密码数据。
- 文章、评论、标签写接口的角色模型，是否需要管理员角色。
- Redis 点赞记录的过期策略，以及数据库更新失败时的补偿策略。
- WebSocket 旧的 `?user=` 身份入口已移除；生产环境 token 传递方式及访问日志脱敏策略待确定。

### 9.1 后续确认与推进
